# Backend architecture

The backend is Node.js 24, Express 5, TypeScript, Drizzle ORM (node-postgres), Neon PostgreSQL, Zod and Better Auth. It uses a layered architecture.

## Directory structure

```
backend/
├── drizzle.config.ts  tsup.config.ts  vitest.config.ts  eslint.config.mjs
├── src/
│   ├── app.ts            # builds the Express app (middleware order, routes); no listen
│   ├── server.ts         # listen + graceful shutdown (closes the pg pool)
│   ├── config/           # env.ts (the only reader of process.env, Zod-validated), cors.ts
│   ├── clients/          # third-party API clients (none yet)
│   ├── cron/             # scheduled jobs (none yet)
│   ├── database/
│   │   ├── index.ts      # pg Pool + drizzle({ schema })
│   │   ├── schema/       # catalog.ts, auth.ts (generated by the Better Auth CLI), index.ts
│   │   ├── migrations/   # drizzle-kit SQL migrations (committed)
│   │   └── seed/         # seed.ts + data/catalog.ts
│   ├── dtos/             # Zod request/response schemas (the API contract) + model → DTO mappers
│   ├── exceptions/       # AppError, NotFoundError, ValidationError
│   ├── lib/              # auth.ts (Better Auth instance), jwt.ts (access token verification), logger.ts (pino)
│   ├── middleware/       # validate, error-handler, not-found, request-logger, rate-limit, auth.middleware, upload.middleware
│   ├── models/           # domain types inferred from the schema + domain rules (deriveStockStatus)
│   ├── repositories/     # Drizzle queries
│   ├── routes/           # Express routers; index.ts mounts /api/v1
│   ├── services/         # use cases and business rules
│   ├── types/            # express.d.ts (Request augmentation), pagination.ts
│   └── utils/            # http-response.ts (sendOk)
└── tests/                # unit/ (mocked repositories), api/ (supertest)
```

## Layers and dependency rules

Requests flow **routes → controllers → services → repositories → database**.

Each layer may import the layers below it, plus `models`, `dtos`, `types`, `exceptions`, `utils`, `config` and `lib`. ESLint rules in `eslint.config.mjs` enforce the import boundaries.

| Layer | Responsibility | Must not |
|---|---|---|
| routes | Declare method and path, attach `validate({...})` and auth middleware, bind controller methods | Call services, repositories or the DB |
| controllers | Read validated input (`validated(req, part, Schema)`), call **one** service method, map models to DTOs, `sendOk` | Contain business rules, touch the DB, catch errors just to reformat them |
| services | Use cases and business rules (curated ordering, related-product ordering, not-found decisions); throw `AppError` subclasses | Import Express, Drizzle or `database/` |
| repositories | Drizzle queries; return models, arrays or `null` | Know about HTTP or throw HTTP errors |
| database | Connection, schema, migrations, seed | Be imported by anything except repositories, `lib/auth.ts`, the seed, and type-only imports in `models/` |
| models | Domain types (`typeof products.$inferSelect` + joined category) and pure domain rules | Redefine table columns |
| dtos | API contract as Zod schemas (`common`, `product`, `category`) and model → DTO mappers | Hold business logic or import repositories |
| middleware | Validation (Zod → 400), central error handling, request logging, rate limiting, auth guard | Contain feature logic |

Express 5 forwards rejected promises to the error handler, so there are no `try/catch` wrappers or async-handler utilities. There is also no DI container: modules export plain objects, and tests mock them with `vi.mock`.

## Request pipeline (`app.ts`)

1. `x-powered-by` disabled, `trust proxy` set to `TRUST_PROXY` hops
2. `pino-http` request logging with `x-request-id`
3. `helmet`
4. `cors` (allowlist from `CORS_ORIGINS`, credentials)
5. `/api/auth/*`: rate limit, then the Better Auth handler. This **must** come before `express.json()`.
6. `express.json({ limit: "100kb" })`
7. `/uploads` static files (`UPLOAD_DIR`, immutable cache)
8. `/health` and `/api/v1` routers
9. `notFound`, then `errorHandler`

## Errors

- Services throw `AppError(status, code, message, details?)` or its subclasses.
- `errorHandler` turns them into `{ "error": { "code", "message", "details"? } }`.
- Body-parser errors become 400 `BAD_REQUEST`.
- Multer errors (file too large, unexpected field) become 400 `VALIDATION_ERROR`.
- Postgres constraint violations (found in Drizzle's `cause` chain) become 409 `CONFLICT` (unique 23505, foreign key 23503) or 400 `VALIDATION_ERROR` (check 23514, not-null 23502). Services should still pre-check for clear messages.
- Anything else becomes a 500 `INTERNAL_ERROR`. It is logged with the request id, and production responses get a generic message.

## Validation

- Request schemas live in `src/dtos/*.dto.ts`.
- `validate({ params, query, body })` parses them and stores the typed output on `req.validated`, because Express 5's `req.query` is read-only.
- Object schemas strip unknown keys, strings are trimmed, and limits are capped (e.g. `limit ≤ 100`, ≤ 24 slugs).

## Auth

- `lib/auth.ts` configures Better Auth with the Drizzle adapter.
  - `baseURL` is the storefront origin.
  - `trustedOrigins` comes from `BETTER_AUTH_URL` and `CORS_ORIGINS`.
  - Cookies are secure in production and default to httpOnly and SameSite=Lax.
  - Email + password sign-in is enabled (8–128 character passwords).
  - The `jwt` plugin issues 15-minute access tokens at `GET /api/auth/token` (claims: `sub`, `email`, `name`, `role`; `iss`/`aud` = `BETTER_AUTH_URL`) and serves `/api/auth/jwks`.
  - The `admin` plugin adds `role` and ban fields to users.
- `lib/jwt.ts` `verifyAccessToken()` checks signature, issuer, audience, expiry and claims with `jose`, using keys from `auth.api.getJwks()` (cached; reloaded when a token names an unknown key).
- `middleware/auth.middleware.ts`:
  - `authorize` reads the `Authorization` header, requires `Bearer <token>`, verifies it and sets `req.user` (the decoded claims). Each failure is a 401 `UNAUTHORIZED`.
  - `authorizeAdmin` runs after `authorize`: 403 unless the token's role is `admin`, then it re-reads the user (`userService.assertActiveAdmin`) so demoted or suspended admins are refused immediately.
  - `auditAdminWrites` logs every non-GET admin request (actor, method, path, status).
- Better Auth's `/api/auth/admin/*` endpoints are blocked in `app.ts` (404); admin features live under `/api/v1/admin` (ADR-016).
- `middleware/upload.middleware.ts` exports `uploadImage` (multer, disk storage in `UPLOAD_DIR`, one image in field `image`, JPEG/PNG/WebP/AVIF, ≤ 5 MB, random UUID filenames). Mount it after the auth middleware so rejected requests never write files.
- Routes attach the middleware; resource-level authorization decisions (e.g. "owns this order") belong in services.
- The seed creates or promotes the admin from `ADMIN_EMAIL`/`ADMIN_PASSWORD`.

## Transactions

The node-postgres driver supports `db.transaction(async (tx) => …)`. Use it for multi-row writes; the seed already does.

## Logging

- `pino` writes JSON in production and pretty output in development. It is silent in tests.
- Cookie and authorization headers are redacted.
- Never log secrets or personal data.
